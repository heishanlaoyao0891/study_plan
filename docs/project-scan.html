  • 后端 go test ./...、go vet ./...、OpenSpec strict validate、前端/管理端 type-check 与三类生产构建全部通过。
  • 13 个已归档 change 均已完成任务；本次归档 delta 已同步到当前主规格。
  • 生产配置对 JWT、WeChat、AI 密钥加密 secret 有启动校验；密码使用 bcrypt；关键并发规则有数据库唯一索引。
  • 代码已经覆盖 H5/微信统一账号、封禁体验、AI 计划、反馈、通知、学习组、计时与打卡等较完整产品面。

主要风险

  • change 堆叠冲突：10 个 Requirement 名称被多个未归档 change 同时修改，AI 主 Requirement 同时被 4 个 change 修改。
  • 归档滞后：4 个 change 已 100% 完成仍留在 active；这会让后续 delta 的基线和归档顺序变得含糊。
  • 检查清单漂移：部分 tasks 仍未勾选，但对应测试已经存在，例如 interval-union 测试。
  • 前端验证缺口：UniApp 已有 5 项导航/认证/AI 契约测试，管理端新增 1 项关键布局契约测试，但两端仍缺少常规组件与交互测试；关键 check-in 页面和 API 聚合文件仍偏大。
  • 验证入口失效：scripts/verify.ps1 默认验证已归档的旧 change 名，且当前环境没有 OpenSpec CLI。
  • AI Agent 后续演进：当前功能 change 已完成；更广泛的 provider 重试策略重构和非关键故障注入矩阵已明确移出本 change，可在独立质量 change 中处理。

已确认难点：AI 生成学习计划总是超时

直接原因：backend/handlers/ai.go 为一次请求设置 12 秒总预算，但外部模型 enrichment 使用固定 8 秒子 deadline。backend/services/ai_provider.go 会采用 context 中更短的 deadline，因此管理台的 request_timeout_seconds 对生成接口无法放宽到 8 秒以上。

复现：模拟 provider 配置为 30 秒并一直等待 context，生成接口在 8.003 秒取消请求并返回本地 fallback。

放大因素：请求要求返回完整计划 JSON、最多包含 30 天任务且输出上限 1024 tokens；每次调用新建 HTTP transport，并在配置校验、client 构造和 dial 阶段重复 DNS/public-IP 检查，都会占用同一个 8 秒预算。

已排除：前端没有设置更短的 request timeout，Nginx 也没有配置小于 8 秒的 proxy timeout；主要超时发生在后端主动取消 provider context。

已实施的解决方案：build-constrained-planning-agent 已接入持久化异步 Planning Job。当前直接创建计划的主链路要求有效 ai_decomposed 蓝图才会发布成功；AI 输出按 10 天以内的批次生成，最长支持 30 天，并在每批完成后保存 checkpoint。截断、JSON/Schema、全局 order 和容量问题会触发精准修复提示与后台 retry_wait，页面关闭不会取消任务。固定 planning_blueprint_v2 模板完整携带规范化用户约束，短周期优先完整覆盖、长周期提高颗粒度，且 Prompt 与校验共享实际时段容量。失败尝试只进入 provider-attempt 运营统计，不消耗用户每日成功生成次数。

架构深化候选

以下候选关注把 shallow implementation 收进更 deep 的 module，以减少跨文件跳转、提高 locality、测试性和 AI 可导航性。这里只确定候选方向，不设计具体 interface。

候选 A：OpenSpec change portfolio 收敛 强烈推荐 · 立即

文件：openspec/changes/*、openspec/config.yaml、scripts/verify.ps1

问题：10 个 active change 同时改 100 条 delta requirements，存在 10 组同名 Requirement 重叠；4 个完成项未归档，验证入口失效，导致“规格基线”这个 interface 比实际 implementation 更难理解。

方向：先恢复验证与状态元数据，再按依赖链归档完成项，把外部验收单独标识；让主规格重新成为唯一稳定基线。

收益：消除归档顺序歧义，减少后续 change 合并冲突，提高规格 locality 与发布可追溯性。

候选 B：权威 Schedule Domain Engine 强烈推荐

文件：backend/handlers/plan.go、schedule_rules.go、recovery.go、handlers/ai.go、services/ai_planner.go

问题：occupancy、overlap、overload、计划移动、恢复预览、AI 排程分散在 handlers 与 services；AI 规划还有独立的 free-slot implementation。理解一个规则需要跨多个 module 来回跳转。constrained planner 的未完成任务也明确要求抽取这些规则。

方向：形成一个 deep 的权威排程 module，让手工计划、批量移动、恢复和 AI 计划共用同一条验证/修复 seam；handler 只做 HTTP adapter。

收益：单一规则源、减少分叉、可做表驱动边界测试，并提高所有排程功能的 leverage。

候选 C：Task + Daily Check-in Lifecycle module 强烈推荐

文件：backend/handlers/study.go、checkin.go、task_rules_test.go、frontend/src/pages/checkin/checkin.vue

问题：任务 start/pause/resume/achieved/complete、session 关闭、每日打卡、reward idempotency 和页面状态同时分散在 1000 行 handler 与 541 行页面。interface 看起来只是若干路由，但 implementation 状态机很深且缺少明确 module 边界。

方向：将状态转换、事务、奖励与阻塞原因收进一个 deep lifecycle module；后端路由与前端页面分别作为 adapter，围绕同一状态模型测试。

收益：并发和幂等规则更可证明，页面不再自行拼装业务状态，降低 20 项 refine 测试债的维护成本。

收益：页面体积下降、错误语义一致、H5/微信差异更容易集中，前端测试可从 workflow module 起步。
